# AftermathBench case 质量纲领

## 为什么要写下这份纲领

2026-08-05 的案例复盘表明：一个 case 可以拥有真实运行时、原生回放、reference recovery、固定策略失败、execution control、完整轨迹和确定性评分，却仍然不适合承担论文的核心结论。

这些工程条件只能说明 case 可运行、可重放、可审计。它们不能自动说明模型面对的是一个根本性的恢复判断，也不能自动说明低分来自模型的恢复推理，而不是来自局部工具语义、评分器精确匹配或不可见事实。

今后以这份纲领约束构造、审计、模型实验和汇报。它不否定既有原生回放和证据工作；它要求把这些能力服务于真正有区分度的决策，而不是服务于越来越复杂的包装。

## 核心判断

一条能够成为论文主证据的 case，必须使领域专家能够用两分钟解释清楚：

> 在同一句表面报错下，为什么状态 A 必须做动作 X，而状态 B 必须禁止动作 X；若弄反，会造成什么真实、明显、可被独立检查的损害？

如果这个问题不能清楚回答，case 可以保留为工程诊断、正控制或方法探索，但不能被叫作强模型恢复推理的核心困难证据。

## 不可替代的四个条件

### 1. 先有决策，再有系统

不得先堆原生对象、图深、参考轨迹和 CI，再从模型的末尾小错中寻找“困难”。先写清楚同一报错下的边界状态、互相冲突的恢复动作和现实后果，再决定是否值得实现。

所需的困难不是“操作很多”，而是“不同边界要求相反的、安全性不能兼得的动作”。例如：

- 一个边界必须补发货，另一个边界补发就是重复履约；
- 一个边界必须补账，另一个边界补账就是重复扣款或账本失衡；
- 一个边界必须保留已发布工件，另一个边界必须阻断/替换损坏工件；
- 一个边界必须保留仍服务流量的旧消费者，另一个边界必须切走它以避免不兼容服务。

### 2. 后果必须是实质性的原生后果

主评分失败应落在真实系统后果上：重复付款、重复发货、库存超卖、账本不平、错误取消已生效承诺、发布错误工件、服务不可用或不兼容。

标题、措辞、标签、字段排列、任意 metadata 精确匹配、只影响 benchmark 自己审计字段的差异，不能单独作为主 case 的失败理由。只有当该值本身是模型可查、产品原生、并会造成实质性下游后果的承诺时，才可以成为强约束。

### 3. 决定性证据必须真的可见

模型必须能通过普通、清楚、稳定的公开工具查到区分边界的全部关键事实。不得依赖隐藏状态、竞态时序、没有说明的工具过滤条件或 evaluator 内部常量。

每次模型失败都要先问：模型是否查到了决定性事实？

- 没查到：这是调查失败，前提是工具确实可清楚查到；
- 查到了但误解：这是状态判断或范围推理失败；
- 范围正确但操作失败：这是执行失败；
- 工具、轨迹和评分器对事实是否可见说法不一致：这是 benchmark 公平性问题，必须隔离审计，不能记作模型失败。

### 4. 评分必须测真实完整性，而不是猜作者意图

评分器可以严格检查真实的原生不变量和外部可观察后果，但不应奖励模型猜中作者偏好的表达方式。

如果模型已经完成所有有意义的业务修复，只因 release 文案、内部 label 或某个没有真实影响的字段与作者样例不同而失败，应先审计 evaluator，而不是把它写进困难结果。相反，若模型完成主目标但制造了重复扣款、重复交付、重复外部事件或破坏共享状态，必须失败。

## 每个候选 case 的一页决策简报

在开始昂贵的原生构建、CI、provider 调用、formal packaging 或 hidden freeze 前，每个候选必须先有一页简报，包含：

1. 模型看到的同一句报错和仍有效的用户目标；
2. 至少两个真实、可回放的边界状态；
3. 每个边界下必须执行和必须禁止的动作；
4. 把 A 的修法用于 B、把 B 的修法用于 A 时，分别会造成的原生损害；
5. 区分边界所需的普通查询，以及每条查询能看到的具体字段/记录；
6. reference recovery 的因果依据，而不是只列操作序列；
7. 评分器检查的最终业务/系统后果；
8. 哪些相近但无实质后果的错误应当被接受或只记为诊断。

没有这份简报，最多做低成本可行性原型，不得投入长时间的证据封装和模型预算。

## 反事实检验优先于复杂度检验

实体数、图深、查询数、reference 长度、固定策略失败和 hard admission 继续保留，但降级为必要条件。主检验应是动作反转：

- 把 state A 的完整修复方案应用到 state B，系统是否出现可见、实质性的损害？
- 反过来是否也成立？
- 该损害是否来自原生运行时，而非 benchmark 私有标签或评分器偏好？
- 模型是否能通过公开工具提前发现应该避免该损害？

若答案不清楚，则该 matched group 没有证明它测量了恢复范围区分。

## 低成本否证，高成本封装

今后的顺序必须反过来：

1. 用一页简报否证“这只是复杂而不难”的设计；
2. 用小型原生原型验证动作反转确实会造成真实后果；
3. 审计所有决定性证据是否清楚可查；
4. 只在上述步骤通过后，才进行完整 replay、reference、fixed policy、模型实验、formal binding 和 hidden freeze。

一旦普通模型的轨迹显示它几乎完成了真实修复、只在任意精确匹配上失分，应立即停止把该 case 加工成 headline hard result，优先审计 evaluator 和工具语义。

## 已有 case 的处理原则

- Kubernetes `state_11` 和 ERPNext manufacturing 的部分轨迹可保留为“过度修复、写后不复查、ownership 判断”诊断；要成为主证据，必须进一步说明错误带来的实质性领域后果。
- Forgejo package r1 的 release metadata 失败，在证明批准元数据可清楚获得且元数据差异有真实下游意义前，只能作为 evaluator/工具语义审计对象。
- ERPNext shared-batch 中若普通工具结果与“已有 pending owner”的评分前提冲突，必须先修复可见性或隔离该边界；不得把它宣传成模型推理失败。
- 强模型全通过的 case 应保留为正控制。它们证明“图大/轨迹长/固定策略失败”不等于模型难，能防止项目自我强化。

## 汇报纪律

今后汇报 case 时，必须展示真实轨迹中的四层信息：失败边界的原生事实、正确恢复的因果理由、模型实际的查询与写入、确定性评分器检测到的真实后果。

不得只报通过率、图指标、固定策略分数或模型最后一句总结。不得把 execution control 成功当作模型自行判断成功。不得把仍有工具可见性、评分语义或异步竞态疑点的模型失败用于强能力结论。

## 这份纲领要防止的事情

它要防止项目把大量时间和 token 用在“把一个已有 case 的 CI、证据、形式化和叙述做得越来越完整”，却没有首先验证该 case 是否真的让模型面对一个有现实含义、相互冲突且可公平判断的恢复决策。

AftermathBench 的价值不在于收集模型的小失误，而在于严格证明：当写操作的真实结果不确定时，模型能否根据可见原生证据，在互相冲突的恢复路径之间选择不会伤害真实系统完整性的那一条。
